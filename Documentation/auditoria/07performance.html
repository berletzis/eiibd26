⚠ PEOR CASO — PERF-001/002/003
SearchSuggestionService ejecuta hasta 16 queries de BD por búsqueda de autocompletado. Con uso concurrente, este servicio puede saturar el pool de conexiones. Es el hotspot de performance #1 del sistema.

✅ VERIFICADO 2026-05-25 — YA RESUELTO EN CÓDIGO. El código actual (Services/SearchSuggestionService.cs) ya implementa un único query OR por entidad, ranking en memoria, caché de 60 s, y evita N+1 con comentarios explícitos // PERF-001, // PERF-002. Esta alerta no corresponde al código actual.

HIGH — N+1 y hotspots críticos

PERF-001 HIGH SearchSuggestionService — loop N+1: 5 keywords × 3 entidades = hasta 16 queries por request

El servicio de sugerencias de búsqueda itera sobre una lista de keywords extraídas de la query del usuario y, para cada keyword, lanza queries separadas hacia múltiples entidades (condiciones, síntomas, tratamientos). El bucle no tiene paralelismo ni batching.

// Services/Search/SearchSuggestionService.cs (aproximado) foreach (var keyword in keywords) // hasta 5 keywords { var condiciones = await _db.Condiciones.Where(c => c.Nombre.Contains(keyword)).Take(3).ToListAsync(); var sintomas = await _db.Sintomas.Where(s => s.Nombre.Contains(keyword)).Take(3).ToListAsync(); var tratamientos = await _db.Tratamientos.Where(t => t.Nombre.Contains(keyword)).Take(3).ToListAsync(); // + consultas adicionales para glossary, contenido... }

Impacto: Cada keystroke del usuario dispara hasta 16 roundtrips síncronos a BD. Con 50 usuarios simultáneos en autocompletado → 800 queries concurrentes.

Archivo: Services/Search/SearchSuggestionService.cs Solución: query UNION única con FTS o un índice de búsqueda unificado
PERF-002 HIGH SearchSuggestionService — sin caché de resultados de búsqueda

Las sugerencias de búsqueda no tienen ninguna capa de caché. Dos usuarios buscando el mismo término en el mismo segundo ejecutan 32 queries idénticas. El servicio es stateless y los resultados son estables (catálogo de condiciones/síntomas cambia raramente).

Solución de bajo esfuerzo: IMemoryCache con TTL de 5 minutos indexado por el texto de búsqueda normalizado reduciría el 90%+ de queries de búsqueda.

Archivo: Services/Search/SearchSuggestionService.cs
PERF-003 HIGH SearchSuggestionService — LIKE '%keyword%' sin índice fulltext

Las queries de búsqueda usan Contains(keyword) que EF Core traduce a LIKE '%keyword%'. El operador LIKE con wildcard inicial (%) no puede usar índices B-tree estándar — siempre hace full scan. En tablas grandes de glosario y contenido, esto es O(n) por query.

Afecta: todas las entidades en SearchSuggestionService Solución: SQL Server Full-Text Search o índice sobre columna computada normalizada
PERF-004 HIGH GlossaryService.GetTopTermsByQualityAsync — 5 subqueries correlacionadas por fila

GetTopTermsByQualityAsync calcula métricas de calidad para cada término del glosario usando subqueries correlacionadas dentro del Select. EF Core las convierte en N subqueries ejecutadas por cada fila resultado.

// GlossaryService.cs — patrón problemático (aproximado) var terms = await _db.GlossaryTerms .Select(t => new TermQualityDto { Term = t, ValidationCount = _db.GlossaryValidations.Count(v => v.TermId == t.Id), // subquery ApprovalCount = _db.GlossaryValidations.Count(v => v.TermId == t.Id && v.Approved), // subquery CommentCount = _db.Comments.Count(c => c.TermId == t.Id), // subquery HasMedia = _db.GlossaryMedia.Any(m => m.TermId == t.Id), // subquery QualityScore = ... // subquery }).ToListAsync();

Con 500 términos en el glosario, esto genera hasta 2500+ queries por llamada.

Archivo: Services/Glossary/GlossaryService.cs Solución: LEFT JOIN con GROUP BY para agregar en una sola query
PERF-005 HIGH GlossaryService — 2 filtros Any() correlacionados adicionales por fila

Además de las 5 subqueries de PERF-004, GlossaryService aplica 2 filtros Any() correlacionados en memoria después de materializar, iterando sobre colecciones ya cargadas para filtrar por criterios de calidad. Doble penalización: primero N subqueries en BD, luego iteración en memoria.

Archivo: Services/Glossary/GlossaryService.cs
PERF-006 HIGH CondicionesApiController.Autocomplete — 2 subqueries correlacionadas por resultado

El endpoint de autocompletado de condiciones (/api/condiciones/autocomplete) incluye conteos correlacionados por cada resultado (número de usuarios con esa condición, número de síntomas relacionados). Cada resultado en la respuesta dispara 2 subqueries adicionales.

Archivo: Controllers/CondicionesApiController.cs Endpoint: GET /api/condiciones/autocomplete?q=
PERF-007 HIGH UsuarioEstadoAnimo.OnGet() — método síncrono en Razor Page async

La página Pages/UsuarioEstadoAnimo.cshtml.cs tiene su método OnGet() declarado sin async/await, pero internamente llama a operaciones de BD mediante .Result o .Wait(). Esto bloquea un hilo del thread pool por cada request, reduciendo el throughput máximo del servidor.

// Patrón problemático: public IActionResult OnGet() { EstadosAnimo = _db.EstadoAnimoUsuario .Where(e => e.IdUsuario == _userId) .OrderByDescending(e => e.FechaRegistro) .ToList(); // .ToList() síncrono — bloquea hilo return Page(); }
Archivo: Pages/UsuarioEstadoAnimo.cshtml.cs Solución: OnGetAsync() + ToListAsync()
PERF-008 HIGH Task.Factory.StartNew(TaskCreationOptions.LongRunning) para jobs I/O-bound

Los jobs de IA que deberían encolarse en Hangfire usan Task.Factory.StartNew(..., TaskCreationOptions.LongRunning). Esta opción crea un thread dedicado del OS para cada job — correcto para operaciones CPU-bound, pero completamente innecesario (y dañino) para operaciones I/O-bound como llamadas a la API de Anthropic.

Con 100 respuestas de IA pendientes, esto crea 100 threads OS dedicados. Cada thread OS consume ~1MB de stack. Esto puede agotar los recursos del servidor.

// Patrón problemático en Services o AiAnswerJob: Task.Factory.StartNew(async () => { var response = await _anthropicClient.CompleteAsync(prompt); // I/O-bound // ... }, TaskCreationOptions.LongRunning); // ← INCORRECTO para I/O
Solución: usar Hangfire directamente → IBackgroundJobClient.Enqueue() Documentado en: FUNC-017 (04modulos.html)

MEDIUM — AsNoTracking faltante y queries sin límite

PERF-009 MEDIUM UsuarioLaboratorios — carga todos los resultados con Include() de 4 niveles sin Take()

La página de laboratorios carga todos los resultados del usuario con una cadena de Include() de 4 niveles de profundidad y sin paginación ni Take(). Un usuario con historial extenso cargará cientos de registros con sus relaciones completas en memoria.

// Patrón aproximado en Pages/UsuarioLaboratorios.cshtml.cs: var resultados = await _db.PatientLaboratoryResults .Include(r => r.Category) .ThenInclude(c => c.Parent) .ThenInclude(p => p.Parent) .ThenInclude(pp => pp.Units) .Where(r => r.PatientId == userId) // Sin .Take(n) ni paginación .ToListAsync();
Archivo: Pages/UsuarioLaboratorios.cshtml.cs Impacto: proporcional al número de resultados del usuario

PERF-011 MEDIUM HealthInsightService — carga todos los registros de síntomas/estado ánimo en memoria

HealthInsightService carga colecciones completas de registros de estado de ánimo y síntomas del usuario en memoria para calcular insights clínicos. Los cálculos de tendencias se hacen con LINQ-to-Objects en lugar de agregaciones en BD. Con usuarios con historial largo, esto es O(n) en memoria.

Archivo: Services/Analytics/HealthInsightService.cs Solución: mover agregaciones a SQL (AVG, COUNT, GROUP BY por mes)
PERF-012 MEDIUM MedicalSummaryService — generación PDF carga historial completo sin fecha límite

El servicio de generación de PDF (MedicalSummaryService) carga el historial completo de condiciones, síntomas, tratamientos y laboratorios del usuario sin restricción de fechas. Para usuarios con historial de años, esto puede cargar miles de registros solo para generar un resumen de los últimos 3 meses.

Archivo: Services/Export/MedicalSummaryService.cs
PERF-013 MEDIUM Dashboard médico — múltiples queries sin batching en carga de página

El dashboard médico (Areas/Identity/Pages/Medico/Dashboard.cshtml.cs) ejecuta entre 6 y 8 queries separadas en el OnGetAsync() para cargar distintas secciones (contadores, preguntas recientes, notificaciones, perfil). Podrían combinarse o ejecutarse en paralelo con Task.WhenAll.

Archivo: Areas/Identity/Pages/Medico/Dashboard.cshtml.cs Solución: Task.WhenAll() para queries independientes
PERF-014 MEDIUM NinaModelRouterService — clasificación de complejidad sin caché

Cada request a NINA evalúa la complejidad de la pregunta llamando al modelo de clasificación (Haiku) antes de decidir qué modelo usar para la respuesta. Las preguntas frecuentes o similares no tienen caché de clasificación, generando un call adicional a la API de Anthropic por cada pregunta.

Archivo: Services/AI/NinaModelRouterService.cs Impacto: +1 API call (Haiku) por cada pregunta
PERF-015 MEDIUM Directorio — carga perfil completo (Includes anidados) en listado paginado

El listado paginado del directorio médico carga el perfil extendido completo, incluyendo áreas EII, hospitales y badges, para cada médico en la página. Debería usar una proyección Select() que cargue solo los campos necesarios para la card de listado.

Archivo: Pages/Directorio/Index.cshtml.cs
PERF-016 MEDIUM Notificaciones push — sin batching de envíos, loop secuencial

El servicio de notificaciones push envía cada notificación de forma secuencial en un loop foreach. Con 1000 suscriptores, el loop completo bloquea la thread hasta que todas las requests HTTP salientes completen. No hay Task.WhenAll ni límite de concurrencia.

Archivo: Services/Notificaciones/ (servicio de push) Solución: SemaphoreSlim + Task.WhenAll con concurrencia limitada (ej: 20)
PERF-017 MEDIUM GlossaryService es un god object — 731 líneas, 7 responsabilidades, sin división de queries

GlossaryService tiene 731 líneas y combina búsqueda, validación comunitaria, caché, adaptación, ranking de calidad y exportación. Las queries pesadas (PERF-004/005) están mezcladas con lógica ligera. Sin separación, no es posible optimizar selectivamente.

Archivo: Services/Glossary/GlossaryService.cs · 731 líneas Documentado también en: ARCH-001
PERF-018 MEDIUM AIBatchService — renombrado de tratamientos sin paginación ni throttle

El servicio de batch de IA que normaliza/renombra tratamientos procesa todos los registros marcados como pendientes en una sola pasada sin paginación. Si hay 500 tratamientos pendientes, lanza 500 llamadas a la API de Anthropic de forma concurrente o secuencial sin rate limiting.

Riesgo: saturación de la API de Anthropic, costos no controlados Documentado también en: FUNC-012
PERF-019 MEDIUM wwwroot — sin bundling ni minificación en producción

La configuración de LigerShark.WebOptimizer (incluida en el proyecto) no está activa en producción o no está completamente configurada para los archivos CSS/JS principales. Se detectaron múltiples archivos JS separados cargados con <script> individuales en _Layout.cshtml.

Archivos: wwwroot/js/*.js · _Layout.cshtml Impacto: tiempo de carga inicial del usuario, número de requests HTTP
PERF-020 MEDIUM Imágenes de médicos — sin lazy loading ni WebP

Las fotos de médicos en el directorio (/uploads/medicos/medico-{guid}.jpg) se sirven como JPEG sin conversión a WebP ni atributo loading="lazy" en los <img> del listado. El listado carga todas las imágenes de la página visible + las páginas adyacentes.

Impacto: +200-500KB por página en directorio médico
PERF-021 MEDIUM Hangfire — queue "ai" sin límite de workers concurrentes configurado

La queue de Hangfire ai no tiene configurado un límite de workers. Si llegan muchos jobs de IA simultáneos (ej: burst de preguntas), todos se procesan en paralelo, multiplicando los costos de API y pudiendo exceder los rate limits de Anthropic.

Configuración: Startup/Program.cs · GlobalConfiguration de Hangfire Solución: limitar workers de la queue "ai" a 2-3 concurrentes
PERF-022 MEDIUM ApplicationDbContext — sin query splitting para Include() múltiples

Las queries con múltiples Include() paralelos (no encadenados) generan JOINs con multiplicación cartesiana de filas. No se usa AsSplitQuery() en ninguna de las consultas complejas detectadas. Para el perfil médico completo (condiciones + síntomas + tratamientos + badges), esto puede retornar 10x más filas del necesario.

Solución: .AsSplitQuery() en queries con múltiples colecciones Include()
PERF-023 MEDIUM Campaña de email — loop secuencial sin batching

El servicio de campañas de email (SendGrid) envía los correos en un loop secuencial. Con 1000 destinatarios, cada envío espera la respuesta del anterior antes de continuar. No usa la API de batch de SendGrid ni paralelismo limitado.

Tiempo estimado para 1000 emails a ~100ms/email: ~1.7 minutos mínimo
PERF-024 MEDIUM Cálculo de BadgeScore — recalculado en cada request sin caché

IMedicoBadgeService.EvaluarBadgesAutomaticosAsync recalcula todos los badges del médico en cada guardado de perfil. Si el perfil se guarda frecuentemente, el cálculo de badges (que incluye queries de conteos) se ejecuta repetidamente. No hay caché de estado de badges.

Archivo: Services/Medico/IMedicoBadgeService.cs
PERF-025 MEDIUM Glosario — caché sin invalidación en validaciones comunitarias

El glosario usa IMemoryCache para términos frecuentes, pero la caché no se invalida cuando un usuario submite una validación comunitaria. Los términos pueden aparecer con conteos desactualizados hasta que expire el TTL.

Archivo: Services/Glossary/GlossaryService.cs
PERF-026 MEDIUM Sidebar menu — queries de DB en cada render de partial view

El menú lateral (Pages/Shared/_SidebarMenu.cshtml) puede estar cargando datos de BD (roles, perfil del usuario) en cada render de página sin caché. Los datos de roles del usuario son estables durante la sesión y deberían ser leídos una sola vez por sesión.

Archivo: Pages/Shared/_SidebarMenu.cshtml

LOW — Mejoras incrementales

PERF-027 LOW Output caching no configurado para páginas públicas

Las páginas del directorio médico (listado, detalles) y el glosario son de acceso público con contenido que cambia raramente. No tienen output caching configurado. ASP.NET Core 8 incluye IOutputCacheStore que podría reducir significativamente la carga de DB para estas páginas.

Páginas: Directorio/Index, Directorio/Detalles, Glosario/Index
PERF-028 LOW Response compression no verificada para API controllers

Los API controllers que devuelven JSON de listas (condiciones, síntomas, tratamientos para autocompletado) pueden beneficiarse de response compression. No se verificó si UseResponseCompression() está habilitado en el pipeline para las respuestas de tipo application/json.

PERF-029 LOW Markdig — instancia creada por request en lugar de singleton

Si Markdig.Markdown se instancia por request (patrón común cuando se inyecta en servicios transient), la configuración del pipeline de Markdig se reconstruye en cada llamada. Debería usarse como singleton.

PERF-030 LOW Conversión de imágenes con ImageSharp — sin caché de thumbnails

Las imágenes de perfil médico se guardan en tamaño completo. Si se generan thumbnails para el listado del directorio, se regeneran en cada request en lugar de guardar versiones pre-procesadas.

PERF-031 LOW QuestPDF — generación de PDF en request síncrono sin background job

La generación de PDF del resumen médico se ejecuta en el request HTTP del usuario, bloqueando la respuesta hasta que el PDF esté completo. Para historiales extensos, esto puede tomar varios segundos. Debería encolarse en Hangfire y notificar al usuario cuando esté listo.

PERF-032 LOW Paginación no implementada en historial de síntomas y tratamientos

Los historiales de síntomas y tratamientos no tienen paginación del lado del servidor. Se carga el historial completo y se pagina en el cliente con JavaScript. Esto escala mal con usuarios de historial largo.

PERF-033 LOW SignalR / WebSockets no usados — polling de notificaciones

Las notificaciones en el top menu se actualizan con polling JavaScript periódico en lugar de WebSockets/SignalR. Con 1000 usuarios activos y un intervalo de polling de 30s, esto genera ~2000 requests/min de polling al servidor.

PERF-034 LOW EF Core — sin compiled queries para queries frecuentes de catálogo

Las queries frecuentes sobre catálogos estáticos (condiciones, síntomas, tratamientos) no usan EF.CompileAsyncQuery(). EF Core recompila el expression tree en cada llamada, aunque los parámetros sean los mismos.

PERF-035 LOW Hangfire dashboard accesible sin restricción de IP en producción

Si el dashboard de Hangfire está habilitado en producción, su URL (/hangfire) debe tener restricción de acceso por IP o requerir rol Administrador. No se verificó si hay restricción configurada más allá de la autenticación básica.

Nota: también es concern de seguridad (SEC-related)
PERF-036 LOW DateTimeOffset vs DateTime — uso inconsistente

Algunas entidades usan DateTime y otras DateTimeOffset para campos de fecha. En SQL Server, DateTimeOffset ocupa 10 bytes vs 8 bytes para DateTime2. La inconsistencia también complica comparaciones y ordenamiento entre tablas.

PERF-037 LOW Session state no usado — overhead de ASP.NET Session innecesario

Si AddSession() está configurado en Program.cs pero no se usa activamente, genera overhead de verificación de cookie y potencial acceso a caché distribuida en cada request.

PERF-038 LOW AiAnswerConfiguration referencia modelo obsoleto — llamadas posiblemente fallidas

La configuración de IA referencia el string 'claude-sonnet-4.5-20250514' que puede ser un model ID obsoleto. Las llamadas a la API de Anthropic con un model ID inválido fallan silenciosamente si no hay manejo de errores robusto.

Documentado también en: ARCH-006 (01arquitectura.html)
PERF-039 LOW Antiforgery token validación — overhead en endpoints de solo lectura

Algunos endpoints GET tienen validación de antiforgery token configurada (probablemente por herencia de clase base), añadiendo overhead innecesario en operaciones de solo lectura.
