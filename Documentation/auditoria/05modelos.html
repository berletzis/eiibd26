⚠️ Hallazgos de Modelos (MDL)
MDL-001 HIGH Naming Models/ — 8+ entidades legacy
8+ entidades con nombres camelCase/lowercase — inconsistente con C# conventions
condiciones, sintomas, tratamientos, condicionUsuario, sintomasUsuario, tratamientoUsuario, estudiosLab, estudiosLabUsuario usan nombres de clase y propiedades en camelCase/lowercase. Todo el resto del codebase usa PascalCase.
Impacto: EF Core puede tener conflictos de convención. Nuevos desarrolladores no saben qué estilo aplicar. Dificulta uso de genéricos y reflection.
Recomendación: En sprint de refactor: renombrar a PascalCase con [Table("nombre_original")] para preservar tabla de BD. Prioridad baja — no es bug funcional hoy.
MDL-002 HIGH Typo Models/estuduiLabUsuario.cs
Nombre de archivo con typo: estuduiLabUsuario.cs
El archivo se llama estuduiLabUsuario.cs (typo: "estudui") pero la clase dentro es estudiosLabUsuario. Nombre de archivo no coincide con nombre de clase.
Impacto: Imposible encontrar el archivo por nombre de clase. Confusión para cualquier desarrollador.
Recomendación: Renombrar a estudiosLabUsuario.cs. Bajo riesgo, acción trivial.
MDL-003 HIGH Tipo incorrecto Models/estudioLab.cs:14
estudiosLab.idPadre tipado como string en lugar de int?
public string idPadre { get; set; } — debería ser int? como todos los demás campos idPadre en el sistema. EF crea NVARCHAR en lugar de INT, rompiendo la jerarquía auto-referencial.
Impacto: La jerarquía de catálogo de estudios nunca funciona. Queries de padre/hijo retornan resultados vacíos silenciosamente.
Recomendación: Cambiar a public int? idPadre + SQL script para ALTER TABLE. Aunque el modelo es legacy (DEAD-004), si se sigue usando requiere corrección.
MDL-004 HIGH Sin DbSet Models/AIRequestLog.cs
AIRequestLog sin DbSet en ApplicationDbContext — tabla no existe en BD
La clase AIRequestLog existe con navegación a Pregunta pero no hay DbSet<AIRequestLog> en DbContext. La tabla nunca se creó en migraciones.
Impacto: Cualquier código que intente usar AIRequestLog via EF lanzará excepción en runtime. El modelo es completamente no funcional.
Recomendación: Agregar DbSet al contexto y configurar FK, o eliminar la clase si el logging de IA se hace de otra forma.
MDL-005 HIGH Sin DbSet Models/SintomasNotas.cs · Models/TratamientosNotas.cs
SintomasNotas y TratamientosNotas sin DbSet — tablas existen en BD pero inaccesibles
Ambas entidades aparecen en el Designer.cs de migraciones (las tablas existen), pero no tienen DbSet en ApplicationDbContext actual. No hay forma de accederlas via EF.
Impacto: Si existe funcionalidad de notas en la app, está completamente rota. Las tablas existen con datos potenciales inaccesibles.
Recomendación: Agregar DbSet<SintomasNotas> y DbSet<TratamientosNotas> al DbContext, o ejecutar DROP TABLE si la funcionalidad fue abandonada.
MDL-006 HIGH Falta [Key] Models/Voto.cs · Models/AIRequestLog.cs
Voto y AIRequestLog sin atributo [Key] explícito en Id (Guid)
EF resuelve el PK por convención pero la ausencia de [Key] hace la intención ambigua y puede causar problemas con herramientas de generación de código.
Impacto: No es bug funcional hoy. Riesgo en herramientas de scaffolding y generadores de DTO.
Recomendación: Agregar [Key] a public Guid Id en ambas clases.
MDL-007 HIGH Nullability Models/Perfil.cs:22-23
[Required] en string? Nombre — causa bug de ModelState documentado en CLAUDE.md
[Required] public string? Nombre { get; set; } — [Required] y el operador ? son contradictorios. Este conflicto es el bug documentado en CLAUDE.md sobre "nunca bindear Perfil como [BindProperty]".
Impacto: ModelState falla inesperadamente cuando Perfil se usa como BindProperty. La causa raíz está en el modelo, no en los page models que lo consumen.
Recomendación: Cambiar a public string Nombre { get; set; } = string.Empty; — no nullable, con [Required] o sin él.
MDL-008 MEDIUM Redundancia Models/Perfil.cs
Perfil tiene campos audit duplicados: FechaCreacion + FechaCreado
Existen tanto FechaCreacion (DateTime, non-nullable) como FechaCreado (DateTime?, nullable), más FechaModificado y UltimaActividad. Cuatro campos de timestamp con propósitos solapados.
Impacto: Código puede escribir a un campo pero no al otro. Queries de auditoría pueden usar el campo equivocado.
Recomendación: Consolidar a FechaCreacion + FechaModificacion. Migrar FechaCreado → FechaCreacion via SQL script.
MDL-009 MEDIUM Nullability Models/condiciones.cs:12 · Models/sintomas.cs · Models/tratamientos.cs
[Required] + string? nombre en 3 entidades de catálogo
Mismo patrón que MDL-007 en los tres catálogos principales: [Required] [StringLength(250)] public string? nombre.
Impacto: Warnings de NRT. Contrato del campo ambiguo para callers.
Recomendación: Cambiar a public string nombre { get; set; } = string.Empty;
MDL-011 MEDIUM MaxLength Models/contenidosRespuesta.cs
ContenidoRespuesta tiene múltiples propiedades NVARCHAR(MAX) por falta de MaxLength
Metas, RespuestaTitulo, RespuestaTextoC, RespuestaTextoL, Slug, URLImagenPrincipal, Autor — todas string sin [MaxLength]. Producen NVARCHAR(MAX) en SQL Server, que no puede indexarse.
Impacto: Slug de SEO no indexable sin MaxLength. Queries de lookup por slug son full table scans.
Recomendación: Agregar [MaxLength] a todos los strings: Slug(500), Titulo(300), URL(500), Autor(200).
MDL-012 MEDIUM FK Faltante Models/Pregunta.cs ✅ STALE — Resuelto en DB-06
Pregunta.UsuarioId sin navigation property ni FK configurada en DbContext
UsuarioId (Guid) está comentado como FK a AspNetUsers pero no hay [ForeignKey], no hay navigation property y no está configurado en OnModelCreating.
Impacto: No se puede hacer Include(p => p.Usuario). Sin integridad referencial: preguntas pueden quedar huérfanas si se borra un usuario.
Recomendación: Agregar en DbContext: .HasOne<ApplicationUser>().WithMany().HasForeignKey(p => p.UsuarioId).OnDelete(DeleteBehavior.Restrict);
✅ RESUELTO (DB-06 · 2026-05-26): FK explícita con OnDelete(DeleteBehavior.Restrict) configurada en ApplicationDbContext.cs. Migración 20260526010111_DB_06_Indices_FK_Explicitas aplicada a producción.
MDL-013 MEDIUM FK Faltante Models/Respuesta.cs ✅ STALE — Resuelto en DB-06
Respuesta.UsuarioId sin navigation property ni FK — mismo problema que MDL-012
UsuarioId es un Guid sin FK constraint ni navigation a ApplicationUser. Mismo gap de integridad referencial que en Pregunta.
Impacto: Respuestas pueden quedar huérfanas. No se puede eager-load el autor de una respuesta.
Recomendación: Configurar FK en DbContext igual que MDL-012.
✅ RESUELTO (DB-06 · 2026-05-26): FK explícita con OnDelete(DeleteBehavior.Restrict) configurada en ApplicationDbContext.cs. Igual que MDL-012. Migración aplicada a producción.
MDL-014 MEDIUM FK Faltante Models/PreguntaEtiqueta.cs
PreguntaEtiqueta sin navigation properties a Pregunta ni Etiqueta
La entidad de relación muchos-a-muchos no tiene navigation properties. Solo se configuran índices y constraint unique, pero no las FK relationships.
Impacto: Imposible usar .Include() para cargar etiquetas de preguntas. JOINs deben escribirse manualmente.
Recomendación: Agregar navigation properties: public Pregunta Pregunta y public Etiqueta Etiqueta
MDL-016 MEDIUM Typo Models/Paises.cs:31
Propiedad VIsibleBuscador con mayúscula incorrecta ('I' en lugar de 'i')
public bool VIsibleBuscador — la I mayúscula es un typo. Debería ser VisibleBuscador.
Impacto: Cualquier generador de código o Swagger producirá el nombre incorrecto. Inconsistencia visual.
Recomendación: Renombrar con [Column("VIsibleBuscador")] para preservar nombre de columna en BD.
MDL-017 MEDIUM Inconsistencia Models/ (proyecto completo)
Soft delete inconsistente: Eliminado vs Borrado vs IsActive — SoftDeleteEntity helper solo funciona con Eliminado
Entidades con Eliminado (bool): condiciones, sintomas, tratamientos, condicionUsuario, Pregunta, Respuesta, etc. Entidades con Borrado (bool): ContenidoCategoria, BannerInicio, Paises, múltiples tablas de relación de Contenido. Entidades con IsActive: NotificationSubscription.
Impacto: El helper SoftDeleteEntity<T> en DbContext solo aplica a "Eliminado". Las entidades con "Borrado" NO son soft-deleted por el utility method, resultando en deletes accidentalmente permanentes.
Recomendación: Estandarizar en "Eliminado" para todas las entidades. Las tablas con "Borrado" requieren SQL ALTER COLUMN. Plan de migración incremental.
MDL-018 MEDIUM Inconsistencia Models/ (proyecto completo)
Inconsistencia de idioma en nombres de campos de auditoría
Modelos legacy: fechaCreado, fechaModificado, fechaEliminado (español camelCase). Modelos nuevos: CreatedAt, UpdatedAt (inglés PascalCase). Algunos: FechaCreado, FechaModificado (español PascalCase). También mezcla DateTime.Now vs DateTime.UtcNow.
Impacto: No se puede escribir utilidades genéricas de auditoría. Confusión sobre timezone.
Recomendación: Adoptar estándar FechaCreacion/FechaModificacion (español PascalCase, UTC) para nuevas entidades.
MDL-019 MEDIUM Tipo incorrecto Models/Glossary/GlossaryValidation.cs ⚠️ FALSE POSITIVE
GlossaryValidation.UserId es string — único caso en todo el sistema (resto son Guid)
Todas las entidades del sistema usan Guid para UserId. GlossaryValidation usa string (NVARCHAR 450). El proyecto usa IdentityUser<Guid> por lo que los IDs son Guids. Almacenarlos como string pierde type safety.
Impacto: No se puede hacer FK JOIN a AspNetUsers con tipo consistente. Pérdida de type safety. Posible incompatibilidad con queries de correlación de usuarios.
Recomendación: Cambiar UserId a Guid. SQL: ALTER COLUMN UserId UNIQUEIDENTIFIER NOT NULL. Migrar datos existentes.
⚠️ FALSE POSITIVE (verificado 2026-05-26): GlossaryValidation.UserId tiene comentario explícito /// ASP.NET Identity UserId (nvarchar 450). ASP.NET Identity almacena el ID del usuario como string en AspNetUsers.Id (NVARCHAR 450). El campo es correcto — es consistente con el tipo de IdentityUser.Id. La auditoría asume IdentityUser<Guid> pero el campo es un string de Identity estándar. No requiere acción.
MDL-022 MEDIUM Redundancia Models/Contenido.cs:25-34
Contenido tiene tres referencias al autor: IdAutor (FK Perfil) + IdUser (FK User) + Autor (string)
IdAutor (Guid FK a Perfil), IdUser (Guid? FK a ApplicationUser) y Autor (string nombre denormalizado). Las tres apuntan al mismo concepto. Datos pueden divergir si el usuario cambia su nombre.
Impacto: Tres fuentes de verdad para el autor de un contenido. Inconsistencia posible.
Recomendación: Remover IdUser (redundante con IdAutor→Perfil.idUser). Marcar Autor como campo legacy/calculado.
MDL-023 MEDIUM Redundancia Models/tratamientoUsuario.cs:10
tratamientoUsuario tiene IdCondicion directa duplicando TratamientoCondicionUsuario
tratamientoUsuario.IdCondicion (FK directa a condiciones) y la tabla de relación TratamientoCondicionUsuario representan el mismo concepto. Un tratamiento puede estar vinculado a una condición por dos mecanismos distintos.
Impacto: Código puede escribir a uno y no al otro. Inconsistencia entre la FK directa y la tabla de relación.
Recomendación: Eliminar IdCondicion de tratamientoUsuario y usar exclusivamente TratamientoCondicionUsuario.
MDL-024 MEDIUM Entidad Duplicada Models/Directorio/DirectorioMedicoConfirmacion.cs · Models/Directorio/ConfirmacionComunitaria.cs
Dos entidades para el mismo concepto: confirmación de médico por paciente
DirectorioMedicoConfirmacion (legacy, sin FK a MedicosDirectorio) y ConfirmacionComunitaria (nueva) representan el mismo concepto de negocio. Ambas tienen DbSet activos.
Impacto: Ver FUNC-023. Los dos flujos de confirmación usan tablas diferentes causando NivelConfianza inconsistente.
Recomendación: Deprecar DirectorioMedicoConfirmacion. Migrar datos a ConfirmacionComunitaria. Eliminar DbSet legacy.
MDL-028 MEDIUM Auditoría Models/TratamientoCondicionUsuario.cs · TratamientoSintomaUsuario.cs · SintomaCondicionUsuario.cs · TrackingSintomaUsuario.cs
Tablas de relación clínica sin campos de auditoría ni soft delete
Las cuatro tablas de relación (síntoma↔condición, tratamiento↔condición, tratamiento↔síntoma, tracking síntoma) solo tienen FechaCreado. Sin FechaModificado, sin Eliminado. TrackingSintomaUsuario no tiene soft-delete.
Impacto: Deletes de tracking son permanentes. Sin audit trail de modificaciones a relaciones clínicas del paciente.
Recomendación: Agregar Eliminado (bool), FechaModificado (DateTime?) y ModificadoPor (Guid?) a las tablas editables.
MDL-015 LOW FK Models/Directorio/DirectorioMedicoConfirmacion.cs
DirectorioMedicoConfirmacion.MedicoId sin FK configurada en DbContext
Sin FK constraint a MedicosDirectorio. Entidad legacy probablemente reemplazada por ConfirmacionComunitaria (ver MDL-024).
Recomendación: Deprecar entidad o configurar FK.
MDL-020 LOW Nullability Models/Etiqueta.cs:20-23
Etiqueta.Fuente y Sinonimos — strings no nullable sin default ni MaxLength
Sinonimos especialmente: sin MaxLength produce NVARCHAR(MAX) no indexable.
Recomendación: Cambiar a string? o agregar = string.Empty. Agregar [MaxLength(2000)] a Sinonimos.
MDL-021 LOW MaxLength Models/SintomasNotas.cs · Models/TratamientosNotas.cs
Nota sin MaxLength — NVARCHAR(MAX)
[Required] public string Nota sin [MaxLength]. NVARCHAR(MAX) para campos de notas clínicas.
Recomendación: Agregar [MaxLength(4000)].
MDL-025 LOW Organización Models/Medico/MedicoBadgeDto.cs · Models/DashboardViewModel.cs · etc.
DTOs y ViewModels mezclados en carpeta Models/ junto a entidades EF
MedicoBadgeDto, DashboardViewModel, BlogViewModels, DirectorioViewModels están en Models/ junto a entidades persistidas. Confusión arquitectónica.
Recomendación: Mover DTOs a carpeta DTOs/ y ViewModels a ViewModels/. Bajo impacto funcional.
MDL-029 LOW Redundancia Models/Voto.cs
Voto tiene Fecha + FechaCreacion + FechaModificacion — tres campos de timestamp
Voto.Fecha es redundante con FechaCreacion. Campo de auditoría duplicado.
Recomendación: Eliminar Voto.Fecha. Usar FechaCreacion exclusivamente.
MDL-030 LOW Nullability Models/condiciones.cs:19 · sintomas.cs · tratamientos.cs · estudioLab.cs
fechaEliminado no nullable en entidades con soft delete
public DateTime fechaEliminado — para registros no eliminados contiene DateTime.MinValue (0001-01-01). Debería ser DateTime?.
Recomendación: Cambiar a DateTime? fechaEliminado en los 4 modelos.
