Directorio Médicos Fase 3 — Propuesta Arquitectónica

Fecha: 2026-05-25  |  Fase: DISEÑO (sin implementación)  |  Precondición: Fase 2 completada

📐 Solo diseño — no hay código ni cambios de BD
Contexto: Tras Fase 2, la fuente única es ConfirmacionesComunitarias. El modelo actual no almacena por qué área EII confirmó el paciente. El Dashboard médico muestra esas áreas vacías. Este documento propone cómo recuperarlas.

Problema

Admin detalle — confirmadores[].exps Áreas específicas por confirmador (ahora muestra TipoConfirmacion) MEDIA
Contadores, badges, nivel confianza Sin pérdida SIN IMPACTO

Solución propuesta — Opción B: ConfirmacionComunitariaArea

Principio: Reutilizar AreaExperienciaEii (tabla ya existe con las 10 áreas). Agregar tabla puente que relaciona cada confirmación con las áreas que el paciente seleccionó. Sin modificar tablas existentes. Sin romper datos históricos.
ConfirmacionComunitaria (1) └──(N) ConfirmacionComunitariaArea ├── ConfirmacionComunitariaId FK → ConfirmacionComunitaria.Id └── AreaExperienciaEiiId FK → AreaExperienciaEii.Id ↑ (ya existe con CUCI, Crohn, etc.)

Por qué no las otras opciones

OpciónProblema
A — FK nullable en ConfirmacionComunitariaUn solo área por confirmación. Un paciente no puede confirmar "Crohn + Biológicos" en un solo acto.
C — Reusar TipoConfirmacion para áreasTipoConfirmacion = quién confirma (paciente, familiar). Áreas EII = qué confirma. Mezclar rompe semántica.
D — Solo agregar a MedicoExperienciaEiiMedicoExperienciaEii es un agregado por médico, no por confirmación. Dashboard necesita datos por fila.

Schema SQL

IF NOT EXISTS (SELECT 1 FROM sys.tables WHERE name = 'ConfirmacionComunitariaArea')
BEGIN
    CREATE TABLE ConfirmacionComunitariaArea (
        Id                         INT IDENTITY(1,1) NOT NULL,
        ConfirmacionComunitariaId  INT NOT NULL,
        AreaExperienciaEiiId       INT NOT NULL,
        CONSTRAINT PK_ConfirmacionComunitariaArea PRIMARY KEY (Id),
        CONSTRAINT FK_CCA_Confirmacion FOREIGN KEY (ConfirmacionComunitariaId)
            REFERENCES ConfirmacionComunitaria(Id),
        CONSTRAINT FK_CCA_Area FOREIGN KEY (AreaExperienciaEiiId)
            REFERENCES AreaExperienciaEii(Id),
        CONSTRAINT UQ_CCA_Conf_Area UNIQUE (ConfirmacionComunitariaId, AreaExperienciaEiiId)
    );
    CREATE INDEX IX_CCA_ConfirmacionId ON ConfirmacionComunitariaArea(ConfirmacionComunitariaId);
END;
