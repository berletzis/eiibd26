ETAPA 1 — FASE 1.1: Auditoría Dashboard Paciente

📅 2026-05-27 🔍 Playwright + code review 📄 Dashboard.cshtml + partials 🎯 /Identity/Usuario/Dashboard

Objetivo de esta fase: Auditoría visual y de código del Dashboard Paciente. Se analiza el estado actual sin modificar nada. Los hallazgos alimentan la FASE 1.2 (Refinamiento).

Metodología: Playwright screenshot (desktop 1440px + mobile 390px) + revisión completa de Dashboard.cshtml, _DashboardColumn1.cshtml, _DashboardNotifications.cshtml y comparación contra el design system (eiibd-tokens.css, eiibd-components.css, eiibd-layout.css, eiibd-utilities.css).

Líneas CSS inline

El Dashboard Paciente funciona correctamente pero acumula deuda técnica visual significativa: aproximadamente 500 líneas de CSS inline en 3 archivos, ninguna usando los tokens del design system (--eii-*). El componente de cards mezcla 4 sistemas visuales distintos (.card, .dashboard-col1-card, .notification-card, .eii-card). Los botones usan 5 clases de herencia distintas. No se usan ni eii-card, ni eii-btn, ni eii-page de los sistemas nuevos.

🔴 Hallazgos Críticos (4)
C-01 — ~500 líneas de CSS inline en partials CRÍTICO

Tres archivos definen sus propios bloques <style> con valores hardcodeados. Esto rompe la consistencia del design system y duplica reglas.

_DashboardColumn1.cshtml → ~250 líneas <style> _DashboardNotifications.cshtml → ~127 líneas <style> Dashboard.cshtml → ~30 líneas <style>

✅ Mover a un archivo dashboard-paciente.css usando tokens --eii-*.

C-02 — 4 sistemas de cards en una sola página CRÍTICO

El dashboard mezcla 4 sistemas de card distintos. El usuario percibe inconsistencia visual.

.card.p-3 → Bootstrap plano (3 cards principales) .dashboard-col1-card → Custom con shadow propio .notification-card → Custom con border-radius: 12px .eii-card → Design system (NO USADO aquí)

✅ Migrar todos a .eii-card o .eii-card--elevated.

C-03 — Cero uso de tokens --eii-* CRÍTICO

Todos los valores de color, espaciado, sombra y radius están hardcodeados. Si cambian los tokens del design system, el dashboard no se actualiza.

#6a4e7a → debería ser var(--eii-primary) #172849 → var(--eii-text-heading) 12px → var(--eii-radius-lg) 0 2px 14px rgba... → var(--eii-shadow-sm)

✅ Reemplazar todos los valores hardcodeados por tokens --eii-*.

C-04 — 5 sistemas de botones distintos CRÍTICO

El dashboard usa 5 clases de botón de distintas generaciones, produciendo inconsistencia visual.

.crm-btn.crm-btn-primary → herencia crm .se-btn.se-btn-primary → herencia se .circle-btn → local inline .btn-add-mood → local inline .btn.btn-outline-primary → Bootstrap

✅ Migrar todos a .eii-btn con modificadores del design system.

🟠 Hallazgos Altos (7)
A-01 — Inline styles en elementos del DOM ALTO

Múltiples elementos usan style="" directamente. Viola las reglas del design system.

<main style="overflow-x: hidden;"> <td style="font-size:.9rem; color:#111827;"> <div style="font-size:.85rem;"> <button style="font-size:28px; border-radius:50%;">

✅ Usar clases utilitarias eii-text-sm, eii-text-muted.

A-02 — Layout sin usar eii-page / eii-grid ALTO

El wrapper principal y el grid son clases locales en lugar de las primitivas del layout system.

<main class="conte-page"> ← local <div class="container py-4"> ← Bootstrap <div class="dashboard-grid"> ← local

✅ Migrar a eii-page y eii-grid del layout system.

A-03 — Cards sin jerarquía visual (planas) ALTO

Las cards de laboratorios, Q&A y PDF usan .card.p-3 de Bootstrap: cero sombra, borde gris plano, padding inconsistente. Dan sensación de UI legacy.

<div class="card p-3"> ← plano, sin shadow ...contenido... </div>

✅ Cambiar a .eii-card--elevated para aire y profundidad.

A-04 — Card headers sin estructura semántica ALTO

Los títulos de las cards usan .dashboard-col1-title con font-size: 1.1rem; font-weight: 400. Peso 400 es débil para un título de sección; no hay jerarquía clara.

.dashboard-col1-title { font-size: 1.1rem; font-weight: 400; ← demasiado débil color: #172849; ← hardcoded }

✅ Usar .eii-card__title + .eii-card__header.

A-05 — Notificaciones con estilo desconectado del sistema ALTO

El panel de notificaciones tiene su propio mini-sistema CSS que no conecta con el design system. El ícono de notificación usa colores solo para warning, no hay variantes por tipo.

.notifications-icon { background: #FFFBEB; ← var(--eii-warning-soft) color: #D97706; ← var(--eii-warning) } /* Sin variantes para info/success/danger */

✅ Definir variantes semánticas con tokens: --eii-*-soft.

A-06 — Tablas densas sin estilos de diseño ALTO

Las tablas de síntomas y laboratorios usan table-sm table-borderless de Bootstrap sin ningún refinamiento visual. Densidad alta, sin hover, tipografía sin tokens.

<table class="table table-sm table-borderless align-middle"> <thead>...</thead> <tbody>...</tbody> </table>

✅ Agregar clase eii-table con hover row y spacing mejorado.

A-07 — Custom select replicado (200+ líneas) ALTO

El componente custom select del modal de estado de ánimo tiene 200+ líneas CSS hardcodeadas con estilos Bootstrap-like. Es un componente duplicado, no reutilizable.

/* En _DashboardColumn1.cshtml */ .custom-select-wrapper { ... } .custom-select-display { ... } ← Bootstrap reset .custom-select-dropdown { ... } /* ~200 líneas de CSS inline */

✅ Extraer a componente reutilizable con tokens.

🔵 Hallazgos Medios (6)
M-01 — PWA push card visualmente prominente MEDIO

La tarjeta de notificaciones push se muestra siempre encima del dashboard con un estilo llamativo que compite con el contenido principal. Resta jerarquía visual.

✅ Reducir prominencia: eii-card--flat con ícono inline sutil.

M-02 — Estado vacío sin componente eii-empty MEDIO

Cuando no hay datos, la tabla muestra texto italic sin estructura visual definida.

<td colspan="4" class="text-muted small" style="font-style:italic;"> No hay resultados para mostrar. </td>

✅ Usar componente eii-empty del layout system.

M-03 — Legend de gráfica sin tokens MEDIO

La leyenda del gráfico de estado de ánimo usa imágenes SVG + texto plano. Podría ser más compacta y usar la escala tipográfica del sistema.

✅ Reducir tamaño de leyenda a eii-text-xs, row gap a --eii-space-3.

M-04 — Botón modal submit con tamaño excesivo MEDIO

El botón de guardar en el modal usa font-size:28px; border-radius:50% inline, haciéndolo visualmente dominante dentro del modal.

<button class="se-btn se-btn-primary" style="font-size:28px; border-radius:50%;">

✅ Cambiar a .eii-btn.eii-btn--primary con tamaño normal.

M-05 — Gap inconsistente entre cards del grid MEDIO

El grid usa gap: 16px hardcodeado. Debería usar el spacing system del design system.

.dashboard-grid { gap: 16px; ← debería ser var(--eii-space-4) }

✅ Reemplazar por var(--eii-space-5) (20px) para más aire.

M-06 — Mobile: cards sin suficiente separación MEDIO

En mobile (390px), las cards se apilan sin suficiente padding lateral. El contenido toca los bordes de la pantalla.

✅ Asegurar padding: var(--eii-space-4) en breakpoint xs.

🟢 Hallazgos Bajos (4)
B-01 — Comentarios legacy en CSS inline BAJO

El archivo Dashboard.cshtml tiene bloques CSS comentados que son ruido:

/* LEGACY — se-page-title migrado a eii-page-title 2026-05 */ /* background: #fff; border: 1px solid #eef2f7; ... */

✅ Eliminar bloques comentados al migrar el archivo.

B-02 — Clase .small-muted sin tokens BAJO

.small-muted es una clase local que solo setea font-weight: 400. No usa tokens ni agrega nada que Bootstrap + utilidades no provean.

✅ Reemplazar por eii-text-sm eii-text-muted.

B-03 — Link de Q&A con URL hardcodeada BAJO

El botón de navegación usa URL hardcodeada en lugar de helper Razor.

href="/Identity/Usuario/UusuarioPreguntaDetalle" /* Typo: UusuarioPreguntaDetalle */

✅ Usar @Url.Page() y verificar nombre de página.

B-04 — @section Head con Google Tag Manager BAJO

El tracking script de Google Tag Manager está incrustado en el archivo de la vista en lugar de cargarse globalmente desde el layout.

✅ Considerar mover GTM a _Layout.cshtml para consistencia.
