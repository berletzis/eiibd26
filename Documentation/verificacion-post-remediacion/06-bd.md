## A. Script SQL: `docs/sql/indices_tablas_clinicas.sql`

### Verificación de Idempotencia

Todos los bloques `CREATE INDEX` usan el patrón `IF NOT EXISTS`:

```sql
IF NOT EXISTS (
	SELECT 1 FROM sys.indexes
	WHERE name = 'IX_condicionUsuario_IdUsuario'
	AND object_id = OBJECT_ID('dbo.condicionUsuario'))
BEGIN
	CREATE NONCLUSTERED INDEX ...
END
ELSE
	PRINT 'Ya existe: ...';
```

✅ **El script es idempotente.** Se puede ejecutar múltiples veces sin error ni duplicado.

El script termina con una query de validación:

```sql

FROM sys.indexes i JOIN sys.tables t ON i.object_id = t.object_id
WHERE i.name IN ('IX_condicionUsuario_IdUsuario', ...)
```

✅ Permite confirmar creación sin depender de PRINT.

## C. Cascade Delete — DB-005: `MedicoAreaEii → Condicion`

### Configuración verificada en `ApplicationDbContext.cs` (líneas 690–703)

```csharp
builder.Entity<MedicoAreaEii>(b =>
{
	b.ToTable("MedicoAreaEii");
	b.HasKey(x => new { x.MedicoPerfilId, x.CondicionId });

	b.HasOne(x => x.MedicoPerfil)
	 .WithMany()
	 .HasForeignKey(x => x.MedicoPerfilId)
	 .OnDelete(DeleteBehavior.Cascade);   // ← Borrar médico → borra sus áreas (OK)

	b.HasOne(x => x.Condicion)
	 .WithMany()
	 .HasForeignKey(x => x.CondicionId)
	 // DB-005: Restrict evita borrado masivo de experiencia médica al eliminar condición.
	 .OnDelete(DeleteBehavior.Restrict);  // ← Borrar condición → ERROR si tiene médicos (PROTEGIDO)
});
```

✅ **`DeleteBehavior.Restrict` está aplicado** en la relación `Condicion → MedicoAreaEii`.

### Simulación del escenario "Admin elimina condición"

Con `Restrict`:

1. Admin ejecuta `DELETE FROM Condiciones WHERE id = X`
2. Si existen filas en `MedicoAreaEii` con `CondicionId = X` → **FK violation → error**
3. La condición **no se elimina** — la experiencia médica se preserva

✅ **Comportamiento esperado verificado en código.**

> ⚠️ **Limitación:** No se ejecutó la simulación contra DB real. La configuración EF es correcta, pero el DB schema existente necesita que la FK de SQL Server esté configurada como `NO ACTION` o `RESTRICT`. Si la columna fue creada antes de esta configuración con `CASCADE`, el comportamiento real puede diferir hasta la próxima recreación de tabla.
