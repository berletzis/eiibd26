Niveles de badge (campo MedicoBadge.Nivel)

El nivel del badge NO es el mismo que NivelConfianza. Es un valor entero en la tabla catálogo que determina qué puede hacer el médico en su dashboard (TienePermisoAsync).

NivelPermiso desbloqueado (TienePermisoAsync)

3ver_nombre_paciente, responder_comentarios

GetNivelActualAsync devuelve badges.Max(b => b.Nivel) — el nivel más alto entre todos los badges ganados.

3. NivelConfianza vs. NivelBadge

Son dos conceptos distintos que frecuentemente se confunden:

ConceptoCampoTipoPropósitoFuente canónica
NivelConfianza MedicosDirectorio.NivelConfianza NivelConfianzaEnum (0–3) Visibilidad pública del profesional en el directorio. Determina qué tag de confianza ve el paciente en el card. ConfirmacionesComunitarias + flags de MedicosDirectorio
NivelBadge GetNivelActualAsync(medicoId) int (0–6) Permisos del médico en su dashboard. Determina qué puede ver/hacer en el área privada. MedicoPerfilBadge → MedicoBadge.Nivel (Max)

Fórmula NivelConfianza (implementada en dos lugares)

static int CalcularNivelVerificacion(int total, bool tieneEII, bool cedulaVerificada, bool perfilReclamado)
{
    if (perfilReclamado)                              return 3; // Establecido
    if (cedulaVerificada || total >= 5)               return 2; // Reconocido
    if (total >= 3 && tieneEII)                       return 1; // Confirmado
    return 0;                                                    // Identificado
}

// tieneEII = total > 0  (plataforma EII: cualquier confirmación implica contexto EII)

Donde se llama RecalcularNivel — DUPLICADO

UbicaciónMétodoSe llama desde
MedicoDirectorioService RecalcularNivelConfianzaAsync(int medicoId) ConfirmarAtencionAsync (después de nueva confirmación)
Admin/DirectorioMedicos/Index.cshtml.cs RecalcularNivelAsync(MedicoDirectorio, int id) (privado) OnPostVerificarCedulaAsync, OnPostEditarAsync (si cambioVerificacion)

⚠ Ambas implementaciones tienen la misma lógica hoy. Si una cambia, la otra quedará inconsistente.

7. Flujos operacionales

A. Paciente propone médico

ProponerMedicoAsync→ Crea MedicosDirectorio
Activo=false, Visible=false→ Estado: Propuesto

No hay badges ni nivel calculado en esta etapa.

B. Paciente confirma atención

ConfirmarAtencionAsync→ INSERT ConfirmacionComunitaria→ RecalcularNivelConfianzaAsync→ UPDATE NivelConfianza

Badge activo_comunidad NO se evalúa aquí. Se evalúa solo cuando admin ejecuta "Evaluar badges".

C. Admin verifica cédula (botón rápido grid)

OnPostVerificarCedulaAsync→ EstatusValidacion = Validado→ RecalcularNivelAsync

⚠ Badge verificado NO se otorga en este flujo.

D. Admin verifica cédula (panel de edición)

OnPostEditarAsync→ cambioVerificacion = true→ EstatusValidacion = Validado→ SaveChanges→ OtorgarBadgeAsync("verificado")→ RecalcularNivelAsync

✓ Badge verificado sincronizado correctamente.

E. Admin aprueba reclamación de médico

OnPostAprobarClaimAsync→ EstatusReclamacion = Reclamado→ NivelConfianza = Establecido (hardcode 3)→ SaveChanges

⚠ NO se evalúan badges. Badge perfil_reclamado no se otorga.
⚠ NivelConfianza se setea directamente a 3 sin pasar por la fórmula canónica.

F. Toggle verificado rápido (botón en grid)

OnPostVerificarAsync→ Toggle EstatusValidacion→ SaveChanges→ Otorgar/Revocar badge "verificado"

✓ Badge verificado sincronizado correctamente. No recalcula NivelConfianza.

9. Discrepancias identificadas

D-01 OnPostVerificarCedulaAsync no sincroniza badge verificado

Escenario: Admin hace clic en el botón "Verificar cédula" del grid (acción rápida).

Resultado actual: EstatusValidacion = Validado, recalcula nivel, pero badge verificado NO se otorga.

Resultado esperado: Igual que OnPostEditarAsync y OnPostVerificarAsync — badge debe sincronizarse.

Fix: Agregar await _badgeService.OtorgarBadgeAsync(m.Id, "verificado", "admin"); en OnPostVerificarCedulaAsync.

D-02 OnPostAprobarClaimAsync no evalúa badges ni delega a fórmula canónica

Escenario: Admin aprueba la reclamación de un médico.

Resultado actual: EstatusReclamacion = Reclamado, NivelConfianza = 3 hardcodeado. Badge perfil_reclamado no se otorga.

Resultado esperado: Se debe llamar EvaluarBadgesAutomaticosAsync (que otorga perfil_reclamado si UserId != null) y recalcular el nivel mediante la fórmula canónica.

Nota: El hardcode de NivelConfianza = 3 es funcionalmente correcto (claim aprobado → Establecido), pero rompe la regla de fuente única y puede divergir si la fórmula cambia.

D-03 Duplicación de RecalcularNivel

Escenario: La misma lógica de cálculo existe en dos lugares.

Lugar 1: MedicoDirectorioService.RecalcularNivelConfianzaAsync — canónico, usa método privado CalcularNivelVerificacion.

Lugar 2: Admin/Index.cshtml.cs:RecalcularNivelAsync — privado, misma fórmula inline.

Riesgo: Si la fórmula cambia (p.ej. nuevo umbral de confirmaciones), el admin podría quedar desincronizado.

Fix: El handler admin debe delegar a _service.RecalcularNivelConfianzaAsync(id) (necesita inyectar IMedicoDirectorioService en el admin).

D-04 OnPostRevocarBadgeAsync en admin duplica lógica del servicio

Escenario: Admin revoca un badge desde el panel.

Resultado actual: El handler duplica 4 líneas de RevocarBadgeAsync en lugar de llamar _badgeService.RevocarBadgeAsync.

Fix: Reemplazar con await _badgeService.RevocarBadgeAsync(medicoId, codigo);.

D-05 Badge perfil_reclamado no verifica EstatusReclamacion

Criterio actual en EvaluarBadgesAutomaticosAsync: MedicoPerfilExtendido.UserId != null.

Problema: Un perfil puede tener UserId vinculado pero EstatusReclamacion = Rechazado o incluso NoReclamado (si el admin vinculó manualmente). El badge se otorgaría incorrectamente.

Fix: Agregar && m.EstatusReclamacion == EstatusReclamacion.Reclamado al join o lookup del profesional.

D-06 Sin trazabilidad de revocaciones de badges

Escenario: Admin revoca badge verificado de un médico.

Resultado actual: Fila de MedicoPerfilBadge se elimina. No queda registro de cuándo, quién ni por qué se revocó.

Impacto: Imposible auditar historial de badges. No hay FASE 3 de trazabilidad sin resolver esto primero.

Opciones: (a) Soft delete en MedicoPerfilBadge con campos Revocado, FechaRevocacion, RevocadoPor; (b) Tabla de log separada.

D-07 EstadoDerivado duplicado en vista paciente

Escenario: Pages/DirectorioMedicos/Index.cshtml.cs:61–67 recalcula la misma lógica inline que ya existe en MedicoDirectorio.[NotMapped].EstadoDerivado.

Fix: Usar directamente m.EstadoDerivado si la entidad se carga completa, o al menos centralizar el cálculo en un helper estático.

Nota: La query usa proyección anónima (solo campos necesarios), por lo que no puede llamar la propiedad [NotMapped] directamente. La solución correcta es hacer el cálculo en el Select() client-side o cargar la entidad completa y usar la propiedad.

10. Resumen ejecutivo

Sistema en estado "funcional pero inconsistente"

El sistema de badges opera correctamente en los flujos más frecuentes (verificar desde el panel de edición, toggle verificar desde el grid). Sin embargo existen 7 discrepancias que producen datos incorrectos en escenarios menos frecuentes pero no excepcionales.

Regla de oro establecida en sesión previa

EstatusValidacion es y debe seguir siendo la única fuente de verdad para "verificado". El badge verificado es un efecto secundario de cambiar ese campo, no tiene semántica propia independiente. Cualquier corrección debe respetar esta regla.

Qué NO tocar

  • La tabla de badges y su catálogo — correcta
  • El método OtorgarBadgeAsync — idempotente y correcto
  • El cálculo de GetNivelActualAsync — correcto para su propósito (permisos del dashboard médico)
  • La fórmula de CalcularNivelVerificacion — correcta, solo necesita un solo punto de invocación

Dependencias entre FASEs

  • FASE 2 (reset query) puede hacerse de forma independiente con la información de este documento
  • FASE 3 (trazabilidad) requiere resolver D-06 (schema change en MedicoPerfilBadge)
  • FASE 4 (revocación manual con confirmación) requiere FASE 3
  • FASE 5 (RecalcularEstadoProfesional canónico) debe consolidar D-03 y el hardcode de D-02
