2. 🚨 Hallazgos Críticos — Alto Impacto

Los siguientes hallazgos producen resultados incorrectos, silenciosos o representan riesgos de seguridad activos.

CRÍTICO-01 "Extremo" ausente del diccionario de analytics
Archivo: eiibd26\Services\Analytics\HealthStatsService.cs · líneas 13–18

Qué está mal:

private static readonly Dictionary<string, int> EstadoSintomaValor = new(...)
{
    ["Ninguno"]  = 0,
    ["Leve"]     = 1,
    ["Moderado"] = 2,
    ["Severo"]   = 3
    // ❌ "Extremo" FALTA
};

Por qué está mal: ValorEstado("Extremo") devuelve -1. Si el primer o último tracking del período tiene estado "Extremo", la función de tendencia ejecuta:

if (primero < 0 || ultimo < 0)
    return new SymptomStatsDto { Tendencia = "Sin datos suficientes" };

Impacto real: Un usuario que está en su peor momento ("Extremo") verá "Sin datos suficientes" en lugar de "Empeorando" — exactamente cuando la alerta clínica es más necesaria. Este error no lanza ninguna excepción. Es completamente silencioso. El PDF también lo reproduce.

CRÍTICO-02 Algoritmo de tendencia clínicamente inválido
Archivo: eiibd26\Services\Analytics\HealthStatsService.cs · líneas 68–93

Qué está mal — 3 problemas anidados:

// Problema A: solo compara primero vs último — ignora todo lo que pasó en el medio
var primero = ValorEstado(trackings.First().Estado);
var ultimo  = ValorEstado(trackings.Last().Estado);
var tendencia = ultimo.CompareTo(primero) switch { > 0 => "Empeorando", ... };

// Problema B: mezcla TODOS los síntomas de TODOS los tipos en una sola serie temporal
var trackings = sintomas.SelectMany(s => s.Trackings).OrderBy(t => t.Fecha).ToList();
  • Problema A: Un paciente Leve → Extremo → Extremo → Extremo → Leve produce "Estable". La tendencia dice que está igual cuando pasó 5 días en estado extremo.
  • Problema B: El primer punto puede ser de "Fatiga" (Leve) y el último de "Diarrea" (Severo). Se comparan síntomas completamente distintos. No tiene validez clínica alguna.
  • Problema C: Este resultado aparece en el PDF y se presenta al médico como un dato analítico de valor clínico.
CRÍTICO-03 CSRF deshabilitado en página de seguimiento matricial
Archivo: eiibd26\Areas\Identity\Pages\Usuario\UsuarioSintomasSeguimiento.cshtml.cs · línea 12
[IgnoreAntiforgeryToken]   // ❌ deshabilita protección CSRF en TODOS los handlers
public class UsuarioSintomasSeguimientoModel : PageModel

Por qué está mal: La anotación a nivel de clase deshabilita la protección CSRF para OnPostTrackSintomaMatrizAsync. Cualquier sitio externo puede realizar un POST autenticado en nombre del usuario, insertando o sobreescribiendo registros de síntomas médicos sin que el usuario lo sepa. Un atacante puede fabricar histórico médico falso.

CRÍTICO-04 Queries de relaciones sin filtro de usuario (riesgo de data exposure)
Archivo: eiibd26\Areas\Identity\Pages\Usuario\UsuarioSintomas.cshtml.cs · líneas 100–120
var relacionesCondiciones = await (
    from rel in _db.SintomaCondicionUsuario
    join cu in _db.condicionUsuario on rel.IdCondicionUsuario equals cu.id
    join c in _db.condiciones on cu.idCondicion equals c.id
    // ❌ SIN WHERE — carga relaciones de TODOS los usuarios
    select new { rel.IdSintomaUsuario, ... }
).ToListAsync();

Impacto: Carga todas las relaciones síntoma-condición de todos los usuarios en memoria del servidor, filtrando en memoria después. Crece O(N_usuarios × M_relaciones). Si en algún refactor se elimina el filtro en memoria, hay data leak real. Igual para relacionesTratamientos.

CRÍTICO-05 Carga de todos los trackings históricos sin límite de fecha
Archivo: eiibd26\Areas\Identity\Pages\Usuario\UsuarioSintomas.cshtml.cs · línea 97
var trackings = await _db.TrackingSintomaUsuario
    .Where(t => t.IdUsuario == userIdGuid)
    .ToListAsync();  // ❌ SIN RANGO DE FECHAS — carga TODO el historial

Impacto: Un usuario activo con 2 años de datos cargará potencialmente miles de registros en memoria solo para mostrar "último tracking" en cada tarjeta. Degradación progresiva y silenciosa del rendimiento.

MEDIO-05 Sin [Authorize] explícito en páginas de usuario
Archivos: UsuarioSintomasModel · UsuarioSintomasSeguimientoModel

Ninguna tiene [Authorize]. Dependen del check manual if (userId == null) return;. Si el middleware global no las cubre, un usuario no autenticado accede sin redirección.

BAJO-01 Riesgo de timezone en toda la cadena de fechas

Toda la persistencia usa DateTime.Now / DateTime.Today (hora del servidor). Si el servidor está en UTC pero el usuario en UTC-6, un tracking registrado a las 11 PM del usuario se almacena como día siguiente. En un PDF médico esto es un error en los datos históricos.

BAJO-02 Lógica de tracking upsert triplicada

El patrón upsert existe idéntico en 3 handlers: OnPostTrackSintomaAsync, OnPostTrackSintomaMatrizAsync (seguimiento), OnPostTrackSintomaMatriz (dashboard). Cualquier cambio de lógica clínica debe hacerse 3 veces con riesgo de divergencia.

4. 📊 Validación de Cálculos

PreguntaResultadoExplicación
¿Los cálculos de rango de fechas son correctos? PARCIAL desde = DateTime.Today.AddDays(-6), hasta normalizado con AddDays(1).AddTicks(-1). Matemáticamente correcto. Riesgo de timezone en producción.
¿El promedio de dolor es correcto? SÍ trackings.Average(x => (double)x.Dolor.Value) — solo incluye registros con valor. Correcto.
¿La tendencia de síntomas es correcta? NO Compara solo primer y último punto. Mezcla todos los síntomas en una sola serie. Clínicamente inválido. "Extremo" además retorna -1 (CRÍTICO-01).
¿El promedio de estado de ánimo es correcto? SÍ estados.Average(e => e.EstadoMood) sobre enum numérico 1–5. Correcto matemáticamente.
¿El síntoma más frecuente es correcto? SÍ OrderByDescending(x => x.Conteo) sobre Trackings.Count. Correcto.
¿El síntoma con mayor dolor promedio es correcto? SÍ GroupBy → Average → OrderByDescending. Correcto.
¿Los top 5 síntomas del dashboard son correctos? SÍ OrderByDescending(x => x.Interacciones).Take(5). Correcto.
¿El PDF incluye el período completo? SÍ Fecha >= desde && Fecha <= hasta con hasta normalizado al final del día. Correcto.
¿El Limit = 500 trunca datos sin aviso? RIESGO BAJO El truncado es declarado visiblemente en el PDF. 500 trackings en 7 días = ~71/día, difícil en la práctica actual.
¿El campo "Extremo" se calcula en analytics? NO No está en el diccionario EstadoSintomaValor. Devuelve -1 y colapsa la tendencia a "Sin datos suficientes".

5. 🧬 Validación Clínica

¿Los resultados tienen sentido clínico básico?

Parcialmente.

  • "Tendencia" como concepto existe pero su cálculo es inválido. Decirle a un médico "Tendencia: Mejorando" cuando el paciente tuvo 5 días en estado Severo/Extremo y solo bajó en el último día es una afirmación clínicamente engañosa.
  • Mezclar diarrea, fatiga y dolor articular en una sola tendencia no tiene equivalente en ningún protocolo clínico de EII. Los síntomas GI (medibles) y sistémicos (subjetivos) deben analizarse separadamente.
  • El campo "Sangrado" solo aplica a síntomas TipoSintoma = 1 (Medible). La validación server-side es correcta. Coherente con el protocolo de EII.
  • "Extremo" fue agregado correctamente al UI pero está roto en analytics. El estado más severo es el único que no genera tendencia real.
  • El PDF no incluye el tipo de síntoma (Subjetivo vs Medible) — un médico no puede distinguir si "Dolor de cabeza" y "Sangrado rectal" se miden con la misma escala. Limitación de presentación.

¿Hay riesgo de malas interpretaciones? — SÍ. El PDF presenta "Tendencia de síntomas: Mejorando" como un dato concreto y analítico, cuando el algoritmo detrás solo compara dos puntos arbitrarios en el tiempo, mezclando síntomas clínicamente distintos.

6. 💣 Riesgos Ocultos en Producción

  1. CSRF activo en seguimiento matricial: Cualquier atacante puede generar registros falsos de síntomas en nombre de un usuario autenticado.
  2. Tendencia "Extremo" → "Sin datos suficientes": Un paciente en su peor momento no muestra alarma en el PDF. Si el médico usa el documento para tomar decisiones de medicación, podría subestimar la gravedad.
  3. Crecimiento de queries sin límite: Con el tiempo, ToListAsync() sin fecha en trackings cargará historial completo. A los 6–12 meses de uso activo, la página de síntomas se volverá lenta de manera progresiva y silenciosa.
  4. Data de todos los usuarios en memoria: Las queries de relaciones sin filtro de usuario pueden cargar datos de cientos de usuarios simultáneamente en una sola request. Riesgo de OOM o degradación general del servidor.
  5. Timezone en datos médicos: En producción con servidor en zona horaria diferente al usuario, los registros de un día pueden aparecer en el día siguiente. En un PDF médico esto genera fechas incorrectas.
